# Прогноз отказа насоса на синтетическом датасете

Данные полностью синтетические. Их сгенерировал скрипт new-gen.py из архива «МРОН datasets.zip» для четырёх насосов NPV_2_1…NPV_2_4. Все цифры ниже относятся к синтетике и о реальных насосах ничего не говорят.

## Итог: run-004 (spec_pumps_v4.txt)

Порог берётся с наибольшим recall при precision не ниже 0,95 на validation. Выбрано среднее бустинга и нейросети MLP. Test открыт один раз для этой версии, всего в четвёртый раз.

| горизонт | test P / R | F1 | доля событий | F1 правила |
|---|---|---|---|---|
| 30 мин | 0,954 / 0,813 | 0,878 | 0,047 | 0,120 |
| 1 ч | 0,954 / 0,826 | 0,885 | 0,091 | 0,190 |

Полнота по типам на горизонте 1 ч: засорение фильтра 0,97, несоосность 0,76, неизвестная неисправность 0,00. Модель отдаёт сервис на /predict_pump (outputs/ml-service/README.md). Выдача сервиса совпала с экспериментом на 20 строках test из 20.

## Результат run-003 (spec_pumps_v3.txt)

Цель команды: precision 0,95. Модель предупреждает об отказе насоса за 30 минут и за 1 час с precision 1,0 на test при recall 0,56. Порог выбран на validation по правилу из spec, test открыт один раз для этой версии.

| горизонт | модель | test P / R | F1 | доля событий | правило P / R | F1 правила |
|---|---|---|---|---|---|---|
| 30 мин | HGB, признаки v3 | 1,000 / 0,561 | 0,718 | 0,047 | 0,072 / 0,351 | 0,120 |
| 1 ч | HGB, признаки v3 | 1,000 / 0,560 | 0,718 | 0,091 | 0,133 / 0,332 | 0,190 |

На validation при P ≥ 0,95 достижима полнота 0,80 (30 мин) и 0,82 (1 ч). Правило выбора порога из spec останавливается на recall около 0,55: при precision 1,0 запас по recall дальше не растёт.

Полнота по типам отказа на test, горизонт 1 ч: засорение фильтра 0,94, несоосность 0,16, неизвестная неисправность 0,00. Хорошо предсказывается только засорение фильтра.

Проверены четыре варианта: HGB на базовых признаках, HGB на признаках v3, нейросеть MLP (64, 32) и их среднее. Базовый HGB до 0,95 не дотягивает (recall 0,38 и 0,45 при P ≥ 0,95), остальные три проходят; выбран HGB с наибольшим запасом.

Почему точность такая высокая: генератор начинает деградацию скачком от нормы и дальше ведёт датчики по детерминированной кривой. По признакам положение строки внутри траектории восстанавливается с R² 0,956, а отсюда и время до отказа. На реальных насосах так не будет, это свойство синтетики.

Горизонты 8 ч и 24 ч не проходят по доле событий (0,52 и 0,9996 при пределе 0,35).

### Предыдущие прогоны недействительны

В run-001 и run-002 «средний шаг» делился на длину доступной истории. Отношение двух признаков давало число строк от начала траектории (R² 0,99), а spec это запрещает. В spec_pumps_v3.txt это исправлено: история до траектории дополняется нормальным профилем насоса. Test основного файла открывался в run-001, run-002 и run-003. Цифры run-003 почти совпали с run-002, так что утечка точность не создавала.

## Как устроены данные

1. Малый файл `(1).csv` (10 000 строк) не подходит. В нём насос и отказ выбираются случайно для каждой строки, а `time_to_next_fault_hours` не связан со следующим отказом: корреляция −0,02.
2. В основном файле (1 236 656 строк) лежат 9 500 траекторий длиной 1, 8 или 24 часа с шагом 5 минут. Метка отказа стоит на последней строке. Все траектории начинаются в 2025-07-14 00:00, поэтому их пришлось собирать заново по порядку строк внутри одного момента времени. Сборку проверяют: длина, одна метка в конце, число строк на каждом шаге.
3. Два файла для повторной проверки собрать не удалось. В них на отдельных шагах строк меньше, чем открытых траекторий, то есть траектории начинаются не с шага 0. По порядку строк это не разрешить. Это другая версия генератора.

## Протокол

Каждая spec (v1, v2, v3) закоммичена до своего прогона. Признаки v3 берутся из текущей строки и предыдущих строк той же траектории: 12 датчиков, тип насоса, изменение за 12, 36 и 96 шагов, ускорение, средние и максимумы по вибрациям и температурам. Недостающая история дополняется медианой нормальных строк насоса из обучающей части. Время, номер шага, `anomaly_score_*`, `status` и поля типа отказа в признаки не входят: генератор считает оценки аномалии прямо из тяжести дефекта.

Выборки делятся по порядку генерации, отдельно по каждому насосу: 60 % траекторий на обучение, 20 % на validation, 20 % на test. Модели по умолчанию, отдельные для каждого горизонта.
