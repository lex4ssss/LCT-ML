# Аудит полного архива

Все годовые архивы прочитаны полностью. История подходит для подготовки временных выборок прогноза записанных тревожных эпизодов. Она не содержит подтверждённой разметки поломок и не доказывает непрерывную наблюдаемость каждого датчика.

## Что проверено

Источник: /Users/work/Downloads/archive. Проверены состав папки и содержимое каждого 7z. В папке находятся годовые архивы ext-journal-2019.7z–ext-journal-2026.7z, пример журнала и справочники каналов, объектов и состояний. Каждый архив содержит один CSV с ожидаемыми колонками.

Режим аудита: полный проход, строгий CSV-разбор и точное сравнение включены; удаление повторов, фильтрация записей, преобразование значений датчиков в числовой тип, обучение и инференс выключены. Даты ниже относятся к исходному локальному времени; Europe/Moscow принят вслед за backend и отдельно не подтверждён владельцем источника.

Прочитано 313 546 017 строк, из них 2 467 812 отмечены тревожными. Период: 1 января 2019 года 00:00:21 — 30 июня 2026 года 23:59:59. Сырые данные сохранены в Parquet в work/archive-audit. Итоговые числа находятся в summary.json, параметры, SHA-256 архивов и дневные агрегаты в годовых JSON рядом с этим файлом.

## Существенные находки

1. **ID события не уникален.** Точный подсчёт по всему архиву дал 307 519 939 различных ID, включая ID единственного повторного заголовка. Внутри отдельных лет есть одинаковые ID с разными каналами или временем. Удаление строк только по ID уничтожило бы разные события.
2. **Точные повторы отделены от совпадений ID.** Сравнение всех исходных полей, кроме позиции строки, обнаружило 563 940 лишних полных повторов: 1 491 в архиве 2019 года и 562 449 в архиве 2023 года. Среди них 834 тревожные строки. Проверены все годы с повторами ID. В остальных годах ID внутри файла уникальны, поэтому полного повтора там быть не может. Валидные даты каждого файла лежат внутри его года, что исключает одинаковую полную запись между разными годами.
3. **Есть разрывы всего журнала.** Записи отсутствуют за 7–8 апреля 2024 года и 1 июня 2026 года. Это установлено по дневным агрегатам и подтверждено отдельным запросом к строкам. Дополнительный полный проход по нормализованному времени с очисткой, без обучения и инференса выявил шесть пауз от часа. Точные границы находятся в log-gap-intervals.json. Самая длинная пауза лежит между 5 апреля 2024 года 22:01:30 UTC и 9 апреля 02:29:49 UTC: исключать только полностью пустые даты недостаточно. Причина отсутствия не установлена. Подготовка ML исключает пересекающиеся с паузами окна по точным границам.
4. **Внутри CSV есть заголовок.** Единственная строка с некорректными датой и признаком тревоги находится в архиве 2025 года. Все её поля точно совпадают с названиями колонок. Она учитывается отдельно и удаляется при подготовке данных. Остальные структурно прочитанные строки прошли проверки времени, ID и допустимых значений признака тревоги по правилам аудита.
5. **Исторические каналы не полностью покрыты текущим справочником.** В валидной истории наблюдались 12 627 каналов, из них 1 142 отсутствуют в текущем каталоге. Все 11 485 каналов каталога встречаются в истории. Сумма несопоставленных сырых строк составляет 9 439 855, включая повторный заголовок. Это число до очистки. Несопоставленные исторические каналы нельзя автоматически приписывать текущим объектам.

## Наблюдаемость и смысл метки

Режим проверки покрытия: весь архив и дневные агрегаты, без удаления повторов, обучения и инференса. У 12 614 из 12 627 каналов есть дни без записей между первой и последней записью. Медианная доля дней с записями внутри такого периода составляет около 8,9%. Это характеристика журнала, не измерение времени работоспособности. Источник может записывать только изменения состояния.

Отсутствие тревожной строки нельзя приравнять к подтверждённой исправности. Рабочая метка относится к началу нового записанного тревожного эпизода. Показатели будущей модели нужно описывать именно для этого события. Известные разрывы всего журнала и неполные временные окна получают неизвестную метку, а не ноль.

Время поступления записи отсутствует. Исторические признаки будут использовать время события; проверка реальной доступности записи онлайн по этому архиву невозможна. Задержки доставки надо учитывать отдельно при интеграции.

## Справочники и пример

Пример журнала и справочник объектов совпали с backend по разобранным CSV-записям. Байтовое содержимое отличается, поэтому совпадение установлено отдельным сравнением записей, а не хешей. В справочнике каналов отличаются 27 названий датчиков; остальные поля совпадают. Для дальнейшей обработки используется справочник из полученного датасета.

Справочник состояний содержит подозрительные сочетания типа и названия состояния: например, у типа «Датчик температуры» есть состояние «Обнаружен газ». Поле «ид_набор_состояний» повторяется для нескольких состояний и не является кодом отдельного значения датчика. Автоматическое сопоставление по этому полю не выполняется. Источник тревожности для текущего target: исходная колонка «тревожное».

В режиме полного аудита без очистки на 2021 год приходится 1 199 639 тревожных строк. Самые крупные дневные значения находятся в мае. Документация команды связывает всплеск с миграцией, но причинность данными не подтверждена. Год не исключается автоматически; его влияние должно проверяться отдельным экспериментом на обучающей и валидационной частях.

Суточный пример относится к августу 2026 года, тогда как годовой архив заканчивается июнем. Пример не добавлен к истории как непрерывное продолжение.

## Воспроизводимость и ограничения проверки

Использована изолированная установка DuckDB 1.5.5. Настройки чтения CSV сверены с [документацией DuckDB](https://duckdb.org/docs/current/data/csv/overview). Данные не отправлялись в модель или внешние сервисы.

profile_archives.py распаковывает один год, сохраняет сырой Parquet, выполняет profile.sql и удаляет только созданный им временный CSV после успешной проверки. Исходные 7z не изменяются. Для нового полного запуска задайте новые пустые каталоги кэша и отчётов:

```bash
work/data-env/bin/python outputs/ml-archive/profile_archives.py \
  /Users/work/Downloads/archive work/archive-audit-rerun outputs/ml-archive/rerun
```

Обычный COUNT(DISTINCT) на всём архиве и попытка общей группировки превысили заданный лимит памяти. Финальный точный подсчёт разделяет ID по хешу, а внутри каждой части сравнивает полные строки ID. Коллизии хеша не смешивают разные ID. Проверка выполнена с лимитом 1 GB и одним потоком; итог находится в global-id-audit.json. После изменения способа подсчёта прошли 20 проверок против независимого Python-множества, включая пустой вход, NULL и Unicode. Содержательные логи smoke-проверок не сохранялись.

```bash
work/data-env/bin/python outputs/ml-archive/count_global_ids.py \
  work/archive-audit outputs/ml-archive/global-id-audit-rerun.json
```

Аудит подтверждает содержимое полученных файлов. Он не подтверждает полноту выгрузки относительно исходной системы, смысл каждого технического кода, исправность оборудования, достоверность текущего каталога для прошлых лет или качество будущего прогноза.
